# IntentLock v1.5.1 Focused Hardening Design

## Goal

Make the current IntentLock release reliably loadable in Chrome, enforce its declared intervention contract, verify every change in GitHub Actions, and publish a versioned GitHub Release artifact without expanding the V1 product scope.

## Scope and product decisions

This is a hardening release, not a redesign. It fixes verified runtime defects and applies only high-impact accessibility and visual-polish changes. The existing dark/light visual direction remains; decorative motion is reduced where it distracts from deliberate work.

An intervention is non-bypassable: continuing on the interrupted page requires a reflection and explicit override. The alternative action ends the session or closes the affected tab; it must not silently dismiss the lock.

## Architecture

### Extension runtime

- Add the MV3 `alarms` permission and retain the existing persisted alarm-restoration behavior.
- Replace the unsupported module content-script entry with manifest-ordered classic scripts. Shared page-tracker and overlay code will expose a narrow global API used by `content.js`; extension pages and the service worker retain ES modules.
- Make overlay and tab-replacement intervention controls share the same payload: required reflection, optional `markRelated`, and explicit end-session action.
- Make the overlay a labelled modal dialog with initial focus, focus containment, safe viewport scrolling, and no Escape-based bypass.

### Tooling and CI/release

- Add a repository-local `package.json` declaring ESM and scripts for test, static verification, packaging, and tag/version validation.
- GitHub Actions runs the test suite on supported Node versions for pushes and pull requests, with minimal read-only permissions and immutable action references.
- A tag workflow validates that `manifest.json`’s version equals the `vX.Y.Z` tag, creates a deterministic ZIP containing only the extension runtime assets, then creates a GitHub Release with that ZIP attached.
- CI will not attempt Chrome Web Store publishing; the deliverable is a downloadable GitHub Release artifact and a load-unpacked development folder.

### UI and documentation hardening

- Repair the malformed onboarding CSS and replace undefined style tokens with existing or explicitly defined semantic tokens.
- Restore keyboard access to custom radio controls; expose selected state and async feedback accessibly; enlarge compact interactive targets where needed.
- Replace broad transitions and continuous decorative motion with short, property-specific interaction feedback. Preserve `prefers-reduced-motion` support.
- Reconcile task status, changelog, storage retention behavior, and the privacy explanation of optional external LLM requests.

## Data, privacy, and compatibility

No new browsing data is persisted or transmitted. `markRelated` continues to store only hostname-level local data. Optional cloud/local LLM providers remain opt-in; the privacy policy will explicitly say that configured providers receive the minimum request context required for classification.

Existing users keep their policy, history, and active-session storage. The content-script refactor changes loading only, not event message names or stored session shapes.

## Verification

Automated verification must cover manifest permissions, classic-script ordering, the shared intervention payload, CSS syntax/token integrity, package contents, and tag/version matching. The existing Node suite remains required.

The release checklist adds a manual Chrome pass: first-run setup, heuristic lock, fallback lock, reflection override and related-domain mark, short time-budget alarm after service-worker restart, keyboard-only settings controls, and reduced-motion behavior.

## Out of scope

- Chrome Web Store publishing or automated store submission
- User telemetry, cloud synchronization, or analytics
- New product features or a wholesale visual redesign
- Automated browser E2E infrastructure; this release establishes a documented manual acceptance pass first
